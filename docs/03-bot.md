## ۲. الگوریتم انتخاب اندازه

تابع سود:

```
f(x) = amountOut(sell, token→KUKI, amountOut(buy, KUKI→token, x)) − x
```

- مقعر (concave) است: کارمزد و impact باعث می‌شوند رشد سود کند شود و بعد منفی.
- جست‌وجوی ternary روی `[1, min(balance, reserve/4)]` با ۱۲۰ تکرار، بعد یک اسکن کوچک حول جواب برای حذف نویز گردکردن.
- جهت معامله فقط وقتی بررسی می‌شود که `spotPrice(buy) < spotPrice(sell)` باشد (token در buy ارزان‌تر باشد).

سقف‌های ایمنی:

- `reserveKuki / 4` — هرگز بیش از ۲۵٪ استخر را جابه‌جا نکنید.
- موجودی کیف پول (اگر `EXECUTE=1`).
- `MAX_TRADE_TON` — سقف دلاری/تونی.

خروجی شامل `grossProfit`, `gasKuki`, `netProfit`, `gapBps` است. فقط `netProfit` ملاک است.

## ۲.۵ گارد سود — معادل ProtoRev

Osmosis ProtoRev در پایان هر بلاک اربیتراژ را شبیه‌سازی می‌کند و فقط اگر سود مثبت باشد اجرا می‌کند. TON تراکنش اتمیک چندقراردادی ندارد، پس این پروژه همان اصل را در سه لایه پیاده می‌کند:

```
لایه ۱: checkPlan()  → اندازه، سود خالص، سهم از استخر، edge، cooldown، circuit breaker
لایه ۲: quote تازه   → قبل از لگ ۱ از خود استخر (getQuote) و از STON.fi
لایه ۳: quote دوباره → بعد از لگ ۱ با مقدار واقعی دریافتی؛ اگر سودنده نبود، token نگه داشته می‌شود
```

`checkPlan` (در `bot/src/strategy/guard.ts`) این شرط‌ها را بررسی می‌کند:

| شرط | دلیل رد |
|---|---|
| `netProfit >= MIN_PROFIT_TON` | `below_min_profit` |
| `amountIn <= MAX_TRADE_TON` | `above_max_trade` |
| `amountIn <= MAX_POOL_SHARE_BPS` از رزرو KUKI | `too_much_of_pool` |
| `edge >= MIN_EDGE_BPS` | `edge_below_floor` |
| cooldown و تعداد خطاهای پیاپی | `cooldown` / `circuit_open` |

نکتهٔ مهم: **quote از خود قرارداد** گرفته می‌شود (`getQuote` getter)، نه از محاسبات محلی. بنابراین اگر رزروها بین دو tick تغییر کرده باشند، `minOut` بر اساس وضعیت لحظهٔ ارسال ساخته می‌شود.

اگر گارد رد کند، **هیچ تراکنشی ارسال نمی‌شود**؛ حتی اگر محاسبهٔ محلی سود نشان داده باشد. این دقیقاً رفتار «معاملهٔ ضررده انجام نده» است.

## ۳. اجرا: دو لگ، نه یک تراکنش

TON تراکنش اتمیک چندقراردادی ندارد. بنابراین:

```
leg1  →  تأیید موجودی token  →  leg2
```

- هر لگ `minOut` دارد؛ اگر قیمت بدتر شود، استخر KUKI **refund** می‌کند و لگ STON.fi با `minAskAmount` رد می‌شود.
- بین دو لگ، ربات موجودی token را poll می‌کند (پیش‌فرض هر ۳ ثانیه، تا ۶۰ ثانیه).
- اگر لگ دوم انجام نشود، ربات token را نگه می‌دارد و در تیک بعدی می‌تواند بفروشد. این «ریسک موجودی» است، نه «ضرر قطعی».

### چرا ArbExecutor نداریم؟

راه‌حل درست برای اتمیک بودن، یک قرارداد `ArbExecutor` است که:

1. بودجه را نگه می‌دارد،
2. swap اول را می‌فرستد،
3. در callback، swap دوم را می‌فرستد،
4. در پایان اگر `balance < start + minProfit` بود، معامله را ناموفق اعلام و سرمایه را برمی‌گرداند.

این کار ریسک قیمت بین دو لگ را حذف می‌کند، ولی خودش یک قرارداد جدید با حالت‌های پیچیده و سطح حملهٔ جدید است. در v0.1 عمداً ساده نگه داشته شده و در نقشهٔ راه v1 است.

## ۵. نکات عملیاتی

1. **اول dry-run.** چند روز لاگ بگیرید و ببینید چقدر فرصت واقعی وجود دارد.
2. **کلید را جدا نگه دارید.** کیف پول ربات فقط باید موجودی عملیاتی داشته باشد، نه خزانه.
3. **Rate limit.** toncenter بدون کلید سریع محدود می‌شود؛ `TON_API_KEY` بگذارید.
4. **Nonce و seqno.** ارسال پشت‌سرهم با یک کیف پول می‌تواند seqno را قاطی کند؛ بین تراکنش‌ها فاصله بگذارید.
5. **پایش.** اگر `leg1 settled` آمد ولی `leg2` نرفت، هشدار بدهید؛ موجودی token باید دستی/خودکار مدیریت شود.
6. **توقف اضطراری.** `EXECUTE=0` و ری‌استارت، سریع‌ترین توقف است.

دموی `demo.js` واقعاً قراردادها را deploy می‌کند، نقدینگی می‌ریزد، یک فرصت ۱۵۰ bps را رد می‌کند (`below_min_profit`) و یک فرصت ۱۱٪ را با دو تراکنش واقعی اجرا می‌کند و P&L را از موجودی on-chain چاپ می‌کند.

- ۱۵ تست ریاضی: دقت `ln/exp`، برابری ۵۰/۵۰ با constant-product، تطابق ۸۰/۲۰ با فرمول شناور، معکوس‌بودن `amountIn`، بهینه‌بودن اندازه در مقابل brute-force.
- ۵ تست venue: پارس پاسخ واقعی STON.fi، رد کردن استخر بدون KUKI، خواندن tuple وضعیت استخر.
- ۶ تست گارد: رد سود کم، سقف حجم، سهم استخر، edge، cooldown، circuit breaker و کف لگ دوم.
- ۱ تست فرمت پیام: ساختار `Either Cell ^Cell` و opcode.
- ۶ تست قرارداد روی TVM (شامل `getQuote`).

## ۷. محدودیت‌ها

- لگ STON.fi با SDK رسمی ساخته می‌شود ولی روی مین‌نت تست نشده؛ اول با مبلغ کم تست کنید.
- ربات به API عمومی وابسته است؛ قطعی API = توقف معامله (نه ضرر).
- ربات MEV-resistant نیست؛ اگر تراکنش شما دیر برسد، دیگران زودتر گپ را می‌بندند.
- هیچ تضمینی برای سود وجود ندارد؛ `simulate.ts` را با دادهٔ واقعی خودتان اجرا کنید.
